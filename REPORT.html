1. Abstract & Executive Summary

Aerospace and spacecraft systems generate complex, heterogeneous, and critical documentation across missions (flight manuals, telemetry specs, anomaly registers, procedural handbooks). Searching across fragmented engineering knowledge bases with standard keyword search frequently fails to surface functional matches and lacks relational context.

COSMOS (AstroRAG) addresses this challenge through a unified Dual-Paradigm Database System combining traditional Relational Database Management Systems (PostgreSQL 16) with vector storage (pgvector). Rather than running isolated vector search services, COSMOS consolidates mission telemetry, documents, vector embeddings, anomaly registers, and tamper-evident audit logs inside a single ACID-compliant database engine. Retrieved context is synthesized using Google Gemini, producing verifiable, cited technical intelligence.

2. Problem Statement & Operational Objectives

  • Relational Context Preservation: Maintain strict relationships between spacecraft missions, engineering disciplines, technical documents, and operational anomaly logs.
  • Semantic Sub-Millisecond Retrieval: Enable dense vector similarity search across technical chunks without losing transactional database guarantees.
  • Auditable Governance & Immutability: Ensure every document upload, revision change, status transition, and resolution is captured automatically via database triggers.
  • LLM Hallucination Mitigation: Ground responses in authorized document excerpts with explicit citation badges.

4. Dual-Paradigm Database Architecture

1. Relational Paradigm: Implements 3NF relational schemas with ACID transactions (BEGIN / COMMIT / ROLLBACK). Document ingestion and chunk vectorization occur within a single transaction boundary, ensuring zero orphaned records upon failure. Foreign key cascades delete chunks when a document is removed, while user and subsystem foreign keys use ON DELETE SET NULL to preserve incident logs.
2. Vector Paradigm (pgvector): Dense 384-dimensional vectors represent normalized text chunks. Cosine distance (<=>) measures semantic angle: D(u, v) = 1 - (u • v). HNSW indexes ensure fast logarithmic-time retrieval over millions of records.

6. Advanced Database Features Implementation

6.1 Vector Retrieval Stored Function (PL/pgSQL)

CREATE OR REPLACE FUNCTION match_spacecraft_knowledge(
    query_embedding vector(384),
    match_threshold float DEFAULT 0.12,
    match_count int DEFAULT 5,
    filter_subsystem_id int DEFAULT NULL,
    filter_mission_id int DEFAULT NULL
)
RETURNS TABLE (
    chunk_id UUID, document_id INT, document_title VARCHAR, file_name VARCHAR,
    subsystem_code VARCHAR, mission_code VARCHAR, chunk_text TEXT, similarity FLOAT, metadata JSONB
)
LANGUAGE plpgsql AS $$
BEGIN
    RETURN QUERY
    SELECT dc.chunk_id, d.document_id, d.title AS document_title, d.file_name,
           COALESCE(s.code, 'GENERAL')::VARCHAR AS subsystem_code,
           COALESCE(m.mission_code, 'GENERAL')::VARCHAR AS mission_code,
           dc.chunk_text, (1 - (dc.embedding <=> query_embedding))::FLOAT AS similarity, dc.metadata
    FROM document_chunks dc
    JOIN engineering_documents d ON dc.document_id = d.document_id
    LEFT JOIN subsystems s ON d.subsystem_id = s.subsystem_id
    LEFT JOIN spacecraft_missions m ON d.mission_id = m.mission_id
    WHERE (1 - (dc.embedding <=> query_embedding)) >= match_threshold
      AND (filter_subsystem_id IS NULL OR d.subsystem_id = filter_subsystem_id)
      AND (filter_mission_id IS NULL OR d.mission_id = filter_mission_id)
    ORDER BY dc.embedding <=> query_embedding ASC LIMIT match_count;
END; $$;

6.2 Automated Database Triggers

  • trg_audit_document_lifecycle: Attached to engineering_documents on BEFORE INSERT OR UPDATE. Automatically writes an audit row to audit_logs capturing document title, status, version changes, and chunk count as structured JSONB.
  • trg_update_anomaly_ts: Attached to anomalies_incidents on BEFORE UPDATE to update the updated_at timestamp automatically upon incident status changes.

6.3 Aggregated Views

  • vw_subsystem_readiness_summary: Combines 5 tables to report total documents, indexed vectors, open anomalies, and critical incidents per subsystem via COUNT(...) FILTER (WHERE ...).
  • vw_document_vector_stats: Summarizes chunk volume, total token counts, and vectorization status per document.
  • vw_anomaly_impact_matrix: Groups incidents across missions and subsystems by severity and resolution window.

7. Retrieval-Augmented Generation (RAG) Workflow

  1. User Query: Engineer enters a technical question in the chat interface.
  2. Embedding: Server computes a 384-dimensional vector representation of the query.
  3. Vector Search: PostgreSQL evaluates the query vector against document_chunks using HNSW cosine distance.
  4. Evidence Injection: Top-K retrieved chunks are formatted with document titles and metadata.
  5. Grounded Synthesis: Server invokes Google Gemini 2.5 Flash with strict instructions: answers must be derived solely from the provided context chunks and accompanied by source citations.

8. Security, Cryptography, & Governance

  • Scrypt Password Hashing: Passwords are never stored in plaintext. They are salted with 16 random bytes and hashed using scrypt with a 64-byte key length. Comparisons use crypto.timingSafeEqual to prevent timing attacks.
  • HMAC-SHA256 Session Cookies: Stateless tokens (<payload>.<signature>) stored in httpOnly, sameSite: 'lax' secure cookies.
  • AES-256-GCM API Key Storage: User Gemini API keys are encrypted at rest using AES-256-GCM with authentication tags.

10. Conclusion

The COSMOS platform demonstrates how an enterprise relational database (PostgreSQL 16) can be expanded into an intelligent semantic retrieval engine using pgvector. By enforcing relational integrity, automated triggers, aggregated views, and LLM grounding, the project provides a performant, auditable, and reliable foundation for aerospace engineering operations.
